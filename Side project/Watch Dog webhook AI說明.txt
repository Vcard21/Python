wait 是什麼？
這個你 P3 很值得理解。

Execute Webhook 有：
wait=false

預設就是 false。

意思大致是：
「Discord，你收到就處理，我不需要你把建立好的 Message 回傳給我。」

成功時通常得到：
204 No Content

也就是：
成功了，但 response body 沒東西。

如果改成：
wait=true

則變成：
「Discord，等你確認 message 建立完，再把結果回給我。」

成功後會得到一個 Message object。Documentation - Discord

所以開發階段我建議：
wait=true

比較容易 debug。

等 WatchDog 穩定了，再考慮需不需要改回 false。

還有一個值得注意的官方細節：`wait=false` 時，如果訊息最後沒有被保存，Discord 不一定會把它當成錯誤回給你；這也是為什麼測試階段 wait=true 更可靠。

5. 回傳值到底會是什麼？
你可以先分成三類理解。
A. 成功，而且 wait=false
通常：
HTTP 204 No Content

意思：
Request 成功，但沒有 response body。

所以如果 Python：
response.status_code

你會看到類似：
204

但：
response.json()

這時沒 JSON 可以解析。
B. 成功，而且 wait=true
Discord 會回：
HTTP success
+
Message Object

概念上可能包含：
message id
content
channel id
author
timestamp
embeds
attachments
...

所以你可以確認：
Discord 實際建立了什麼訊息。

官方明確規定 Execute Webhook 會依 wait 回傳「message」或 204 No Content。Documentation - Discord
C. Request 有問題
例如：
JSON 格式不合規
content 太長
缺少必要 message content
Webhook URL/token 無效
Discord rate limit
network timeout

那就會得到非成功 HTTP response，或在 Python requests 層直接丟 network exception。

所以你之後 error handling 可以分成兩層：
requests 層
→ 我有沒有成功連到 Discord？

Discord HTTP 層
→ Discord 接到後，有沒有接受這個 request？


在 Python（以及所有網路通訊協定）中，呼叫 Discord Webhook 必須使用 POST 而不是 GET，核心原因在於 HTTP 協定的設計規範 以及 資料傳輸的安全性與容量限制。

1. HTTP 協定的語意分工

在網路通訊的標準中，不同的請求方法代表不同的動作目的：
• GET（讀取資料）。設計用來向伺服器「索取」資訊，例如打開網頁、查詢搜尋結果，理論上不應該改變伺服器的狀態或產生新資料。
• POST（提交資料）。設計用來向伺服器「傳送」新資料並要求處理，呼叫 Webhook 的本質是「要求 Discord 在頻道裡新增一則訊息」，這屬於建立新資源的動作，因此符合 POST 的定義。

2. 資料承載方式與長度限制

兩者在傳遞資料的位置與容量上有巨大的差異：
• GET 把資料放在網址（URL）裡。資料會直接接在網址後面（例如 ?content=你好），但瀏覽器與伺服器對網址長度都有嚴格限制（通常在 2,000 個字元左右），如果遇到長篇文章或複雜的 Embeds 卡片結構，網址會直接被截斷而失敗。
• POST 把資料放在請求主體（Body）裡。資料被打包在封包的內部（也就是你在 Python 中寫的 json=data），幾乎沒有長度限制，也能輕鬆支援結構化的 JSON 格式或上傳圖片檔案。

3. 安全性考量

• 保護敏感資訊與內容。使用 GET 時，所有參數都會明文暴露在網址列中，容易被瀏覽器歷史紀錄、伺服器存取日誌（Access Log）或網路設備記錄下來。
• 避免誤觸與快取。GET 請求很容易被瀏覽器預先載入（Prefetch）或快取（Cache），如果發送訊息用 GET，可能會導致系統在不知情的情況下重複發送相同訊息。
